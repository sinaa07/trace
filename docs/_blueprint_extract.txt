Engineering Reference Document
A concise, implementation-oriented blueprint for the TRACE railway accident investigation platform. The document
deliberately separates MVP/Core, Advanced, and Future/Research scope and prioritizes free, lightweight, and low-
complexity technologies.

Primary design principle
No TRACE finding should exist without an evidence path: Finding → Hypothesis → Causal relationship → Events →
Evidence records → Original source.

1. Project Definition & Design Principles
TRACE is an AI-assisted railway accident investigation platform that integrates heterogeneous railway evidence,
reconstructs a consistent accident timeline, investigates competing hypotheses, identifies causal relationships, and
produces evidence-traceable findings.

Core investigation questions
   What happened? — reconstruct a unified temporal sequence.
   What evidence supports it? — correlate observations and preserve provenance.
   What could have caused it? — investigate competing hypotheses independently.
   How did factors interact? — represent and analyze causal relationships.
   What remains unknown? — expose missing and contradictory evidence.
   Why does TRACE believe this? — provide an evidence-linked explanation.

Design principles
   Evidence first: deterministic evidence processing precedes LLM reasoning.
   Evidence ≠ event: original artifacts, parsed records and normalized events are separate concepts.
   LLM ≠ evidence: model-generated reasoning never becomes evidence by itself.
   LLM confidence ≠ Bayesian probability: they remain separate quantities unless explicitly calibrated.
   Human-in-the-loop: TRACE assists investigation; it does not declare legal responsibility or prove causation.
   Explainability by construction: every finding stores supporting, contradicting and missing evidence references.
   Simple first: use rules and deterministic/statistical methods before expensive models.
   Modular scalability: start as a modular monolith and separate services only when workload requires it.

6. Normalization & Event Model
The event model is the central contract between heterogeneous railway data and every downstream component.

Example normalized event
 {
     "event_id": "EVT-001245",
     "event_type": "SIGNAL_STATE_CHANGE",
     "timestamp": "...",
     "source_id": "SIGNAL-01",
     "entity_id": "TRAIN-102",
     "location": {"track": "T12", "position": 1832},
     "attributes": {"signal": "S42", "state": "RED"},
     "temporal_confidence": 0.96,
     "evidence_refs": ["EVID-004"]
 }


Normalization pipeline
 Raw source
  → schema detection
  → field mapping
  → timestamp parsing
  → entity normalization
  → unit normalization
  → event extraction
  → evidence references


Tools

7. Temporal Reconstruction Engine
Temporal reconstruction is TRACE's main technical differentiator. The engine converts heterogeneous timestamps and
asynchronous observations into a unified investigation timeline.

MVP pipeline
 Timestamp parsing
       ↓
 Timezone normalization
       ↓
 Clock offset estimation
       ↓
 Clock drift / affine correction
       ↓
 Discrete event alignment
       ↓
 Unified timeline


Continuous signals
DTW should not be applied to every event. Discrete events such as signal changes, brake actions and maintenance
records should use timestamp/anchor matching. DTW is reserved for asynchronous continuous signals such as speed,
acceleration or braking curves.
 Feature                       Status                         Preferred                        Alternative
 Time parsing                  MVP                            python-dateutil + zoneinfo       Pendulum
 Offset estimation             MVP                            NumPy/SciPy                      statsmodels
 Anchor matching               MVP                            Python + nearest-time logic      SciPy KD-tree
 Clock drift                   MVP                            scipy.stats.linregress           statsmodels OLS
 DTW                           Advanced                       tslearn                          dtaidistance
 Timeline display              MVP                            Plotly React                     D3.js


Correction model
 corrected_time = a × raw_time + b

 a = drift factor
 b = clock offset

Every corrected event stores original timestamp, corrected timestamp, estimated offset/drift and temporal confidence.

10. Evidence Arbitration & Hypothesis Ranking
Each domain agent returns a structured HypothesisFinding rather than an unrestricted narrative.
 HypothesisFinding
 ├── hypothesis
 ├── supporting_evidence[]
 ├── contradicting_evidence[]
 ├── relevant_events[]
 ├── missing_evidence[]
 ├── assumptions[]
 ├── reasoning_summary
 ├── confidence
 └── uncertainty


MVP ranking dimensions
 Dimension                                                    Meaning
 Evidence support                                             How strongly retrieved evidence supports the hypothesis
 Temporal consistency                                         Whether the hypothesis fits the reconstructed sequence
 Source reliability                                           Reliability assigned to the evidence source/type
 Causal support                                               Whether graph relationships support the proposed contribution
 Evidence completeness                                        Penalty for important missing evidence
 Contradiction penalty                                        Penalty for strong conflicting observations


Important methodological rule
Agent confidence should not automatically become a Bayesian probability. In MVP, use a transparent weighted
evidence score. Bayesian inference is an Advanced module with explicitly defined probability assumptions.



Advanced arbitration
Dempster-Shafer combination may be added when TRACE needs formal combination of uncertain/conflicting evidence. It
should be implemented only after the basic scoring pipeline is validated.

12. Counterfactual Analysis
Counterfactual analysis is Advanced. It should not be implemented as simply deleting a node and rerunning a graph.

Correct conceptual workflow
 Observed evidence
       ↓
 Defined causal model
       ├──────────────┐
       ▼               ▼
 Actual scenario    Intervention do(X=x')
       │               │
       ▼               ▼
 Actual outcome     Counterfactual outcome
       └──────┬───────┘
               ▼
         Outcome difference


Example
Actual: braking begins at time T. Counterfactual: braking begins 5 seconds earlier. TRACE evaluates how the modeled
trajectory/outcome changes under that intervention.

Tools
 Feature                       Status                        Preferred                             Alternative
 Causal intervention           Advanced                      DoWhy                                 EconML / custom SCM
 Probabilistic model           Advanced                      pgmpy                                 PyMC
 Scenario comparison           Advanced                      Python + stored simulation state      custom domain simulator


Reporting language
TRACE should describe results as model-based counterfactual evidence. It should not claim that a counterfactual
experiment proves real-world causation.

13. Conflicts, Evidence Gaps & Rule-Based Anomalies
These features are inexpensive and were strongly informed by the previous forensic project. They should be Core rather
than postponed.

A. Evidence conflict detection
     Signal log says RED while another source reports GREEN at the same aligned time.
     Maintenance report says normal while sensor evidence indicates abnormal condition.
     Two sources assign incompatible states to the same entity/event.
     A reported event occurs at a time inconsistent with another high-confidence event.

B. Rule-based railway anomalies
    Rule                                                         Example
    Impossible sequence                                          Brake release recorded before brake application
    Speed threshold                                              Train speed exceeds permitted threshold
    Temporal prerequisite                                        Collision recorded before train entered section
    Maintenance interval                                         Inspection overdue beyond configured threshold
    Signal transition                                            Invalid or unexpected signal-state transition
    Physical plausibility                                        Sensor value outside configured physical range
    Clock inconsistency                                          Source timestamp moves backward unexpectedly


Implementation
Start with plain Python rules and configuration files. A rule should return rule_id, severity, affected events, evidence
references and human-readable explanation.

C. Evidence gaps / Known Unknowns
    KNOWN UNKNOWN

    Missing:
    Brake diagnostic record

    Impact:
    High

    Affected hypotheses:
    Delayed braking
    Brake-system failure

    Recommended next evidence:
    Brake-system diagnostic / maintenance record

18. Testing, Evaluation, Scalability & Risks
Evaluation should be modular rather than relying on one overall 'accuracy' number.
    Module                                                      Metric
    Evidence parsing                                            Parsing success rate
    Event extraction                                            Precision / Recall / F1
    Clock correction                                            Mean absolute timestamp error
    Event ordering                                              Ordering accuracy
    Rule anomalies                                              Precision / Recall / false-alarm rate
    Conflict detection                                          Precision / Recall
    Hypothesis ranking                                          Top-1 / Top-3 accuracy
    Graph                                                       Relationship accuracy / query latency
    Traceability                                                % findings with valid evidence paths
    System                                                      End-to-end case processing time


Synthetic dataset strategy
     Generate controlled accident cases with known causal chains.
     Create multiple source clocks with intentional offsets/drift.
     Inject missing records and contradictory observations.
     Vary evidence quality and source reliability.
     Keep ground-truth event order and causal factors hidden from the system during testing.

Scalability path
    MVP:
    Modular monolith + PostgreSQL + Neo4j

             ↓ if processing grows

    Background job queue + worker

             ↓ if services become bottlenecks

    Separate evidence / temporal / investigation services

             ↓ at real deployment scale

    Object storage + event bus + distributed workers


Risks and mitigation
    Risk                                                        Mitigation
    LLM hallucination                                           Evidence-grounded retrieval + structured output + human review
    False causality                                             Separate correlation from causal claims; use explicit causal model
    Bad timestamps                                              Store raw + corrected timestamps and temporal confidence
    Missing evidence                                            Known-unknown panel + completeness penalty
    Conflicting evidence                                        Explicit contradiction objects; never silently merge
    Overengineering                                             MVP-first feature freeze
    High API cost                                               Local/free model fallback; cache structured results
    Graph complexity                                            Small typed schema; add algorithms only when justified
    Data privacy                                                Local deployment and controlled evidence access

Advanced feature gate
Do not begin advanced work until the complete MVP workflow succeeds on at least one fully synthetic end-to-end
accident case and all major findings can be traced back to source evidence.



Advanced order of implementation
1. DTW → 2. Bayesian Network → 3. Dempster-Shafer → 4. semantic retrieval → 5. counterfactuals → 6. similar-case
retrieval → 7. dynamic agents.

Final TRACE identity
TRACE is not an LLM that writes an accident story. It is a structured investigation pipeline in which deterministic
evidence processing, temporal reconstruction, domain-specific agents, graph reasoning and human review work
together to produce evidence-grounded hypotheses.

Reference basis: This blueprint incorporates lessons from the previously reviewed ADCSIS project, particularly its case-
centric workflow, evidence integrity, graph-path exploration, hypothesis comparison, explainability, auditability and
human-in-the-loop approach. The previous project also demonstrated the importance of explicitly documenting
implementation limits rather than treating every proposed architecture component as implemented.
